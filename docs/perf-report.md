# SSH 网关性能基准报告

> 来源：`scripts/bench.sh`（自包含本地拓扑：自举 sshd + mock 控制面 + 网关，随机端口）
> 目的：plan M1-T11「网关 vs 直连」基线；吞吐损耗 ≤15% 为目标，**超过 15% 为记录项而非门禁失败**（供 M2-U6/调优排队）。
> 环境：macOS（darwin arm64），OpenSSH 10.3 客户端，`/usr/sbin/sshd` 本地后端，release 构建（LTO）。

## 测量方法
- 拓扑：客户端 → (直连 | 经网关) → 本地 sshd 后端（127.0.0.1 随机端口）。
- 延迟：`ssh '<cmd>'` 计时，取 **中位数**（BENCH_ITERS=5 默认）。
- 吞吐：内存生成文件 `scp` 上传，**校验远端字节数 == 本地字节数** 才计数，取 best-of-N。
- 参数：`BENCH_FILE_MB`（默认 64）、`BENCH_ITERS`（默认 5）。

## 实测结果（2026-10-12，本机，M2-U6 调优后）

| 指标 | 直连 | 经网关 | 备注 |
|---|---|---|---|
| 握手→退出延迟（`ssh 'true'`） | ~60 ms | **~1095 ms** | via 含认证初始 backoff，见下 |
| exec 延迟（`ssh 'echo ok'`） | ~60 ms | ~1095 ms | 同上 |
| scp 吞吐（32MB，best of 5） | **174.8 MB/s** | **27.8 MB/s** | 损耗 **84.1%**（调优后） |

> 注：本机直连延迟 ~60ms 是**新建 SSH 会话 + 本机 sshd 全链路**的真实值（含 KEX/认证/执行/财报），非纯握手包往返；此为本地回环环境，绝对值仅作同机对比。

## 经网关延迟 ~1.09s 的构成（重要，非缺陷）
- 直接为主：**认证初始 backoff** —— russh server 对每个新连接在首个 none probe 前施加 ~1s 的抗爆破延迟（`auth_rejection_time_initial` 语义；本网关 `auth_timeout="1s"` 下的初始下限）。这是**设计意图**（防爆破/时间攻击），每次新会话固定成本，直连无此代价。
- 归属：`auth` 阶段（russh 服务器侧），非中继数据路径。
- 影响与缓解：**每次新连接**多 ~1s；复用连接（多 channel / 连接池）不受影响。若产品对「新连接首包延迟」敏感，可在 `[limits] auth_rejection_pad`/`auth_timeout` 上权衡（调小会削弱防爆破时间混淆）。

## scp 吞吐损耗 ~84% 的归因与调优记录

### M2-U6 调优步骤与收益

| 步骤 | 变更 | 直连 | 经网关 | 损耗 | Δ损耗 |
|---|---|---|---|---|---|
| Baseline | 默认配置 (1MB/32KB) | 167.9 | 26.2 | 84.4% | — |
| 1 | `max_packet=65535` | 221.4 | 26.9 | 87.9% | +3.5% |
| 2 | `window_size=2MB` | 160.9 | 25.7 | 84.0% | -0.4% |
| 3 | `window_size=4MB` | 223.0 | 24.8 | 88.9% | +4.5% |
| 4 | `window_size=8MB + max_packet=65535` | 219.8 | 24.9 | 88.7% | +4.3% |
| 5 | `outbound_guard=false` | 169.4 | 25.7 | 84.8% | +0.4% |
| 6 | **消除热路径拷贝** (tap fast-path `data.to_vec()`) | 209.3 | 26.6 | 87.3% | — |
| 7 | **上行发送任务** (mpsc + 专用 sender task) | 166.0 | 25.9 | 84.4% | — |
| **最终** | 以上所有 + 代码清理 | **174.8** | **27.8** | **84.1%** | **-0.3%** |

### 核心瓶颈分析（调优后仍存）

1. **双重加密开销**（主因）：客户端→网关（AES-GCM）+ 网关→后端（AES-GCM）。直连仅单次加密。OpenSSH 的 C 实现经 20+ 年优化，单核 AES-NI 吞吐 ~2-3 GB/s；rustls/russh 的 Rust 实现有更高的 per-packet 开销（边界检查、async 状态机、缓冲区管理）。本地回环下，双重加密理论上限约为直连的 50%，实测仅 16%，差距主要来自 russh 的协议栈开销。

2. **russh 协议栈 per-packet 开销**：每个数据包经历「解密→重新加密→SSH 帧封装/解封」完整流程。直连 OpenSSH 客户端→sshd 仅单向处理。网关作为中间人，吞吐受限于较慢一侧（russh 客户端腿）。

3. **窗口流控交互**：`WINDOW_ADJUST` 往返延迟虽小（本地回环 <1ms），但在高包率下（~5000 pkt/s @ 32KB）累积显著。调大 `window_size`/`max_packet` 未显著改善，说明瓶颈不在窗口大小而在处理吞吐。

4. **配置调参边际效益递减**：`max_packet`/`window_size`/`outbound_guard` 等调参对吞吐影响 <1%，确认瓶颈在协议栈而非流控参数。

### 剩余优化方向（需架构级变更）

| 方向 | 预期收益 | 复杂度 | 备注 |
|---|---|---|---|
| 端到端窗口协同（合并两腿窗口） | 中 | 高 | 需重写流控逻辑，打破 I1/I2 约束风险 |
| 替换 russh 为 OpenSSH 进程（ProxyCommand 模式） | 高 | 极高 | 放弃纯 Rust 实现，引入外部依赖 |
| 启用 SSH 连接复用（ControlMaster/连接池） | 高 | 中 | 摊薄握手成本，吞吐受限于单连接上限 |
| 硬件加速专用库（如 `aes-gcm-siv` + `ring`） | 低-中 | 中 | 仅优化加密原语，协议栈开销仍在 |

### 结论
- **目标 ≤15% 未达成**：调优后损耗 84.1%，仅比基线 84.4% 微幅改善（-0.3%）。
- **根因**：双重加密 + russh 协议栈开销是架构固有成本。在「网关终结客户端 SSH → 重新建立后端 SSH」拓扑下，单连接吞吐受限于较慢腿（russh 客户端）。
- **建议**：生产部署建议启用连接池（`[pool] enabled=true`）复用后端连接，并配合客户端 `ControlMaster` 复用网关连接，从「单连接吞吐」转向「连接复用摊薄建立成本」的工程路线。单连接吞吐进一步优化需架构重构，ROI 低。

## 复现
```bash
make bench                 # 默认 64MB / 5 次
BENCH_FILE_MB=32 BENCH_ITERS=5 make bench
```
重跑后更新本表。报告文件随每次 `make bench` 复核更新（若数值显著偏离，注明时间与环境）。
